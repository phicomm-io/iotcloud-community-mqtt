# TMCP 平台迁移与走查

TMCP 是 Tom MQTT Cloud Protocol。用户界面只显示 TMCP；协议元数据为 `protocol: tmcp`、`protocol_version: 2`、`version: v2`。Legacy 使用 `v1`，仅支持 TC1。

## 数据迁移

旧部署以 Mosquitto `passwd` 和 `acl` 为账号、归属的权威来源；`mosquitto.db` 是消息持久化文件，不是业务账号库。迁移前备份整个部署目录，并单独校验 `passwd`、`acl` 的 SHA-256。备份包含密码哈希和配置密钥，必须存放于仓库忽略的私有目录。

```sh
cd platform/backend
go build -o /tmp/tmcp-platform .
/tmp/tmcp-platform migrate --passwd /private/source/passwd --acl /private/source/acl --output /private/new-runtime
```

迁移器拒绝覆盖已经初始化的目标目录，保留原始密码哈希、盐与迭代次数，不要求普通账号重设密码。原始账号文件另外保存在目标 `backup/`。管理员使用新实例的 `secrets/admin-password` 初始化；它是独立于普通账号迁移的步骤，支持迁移既有管理员密码，内部 Broker 管理密钥仍由工具随机生成。

- 相同账号、相同 MAC 的多个大小写/分隔符 ACL 合并为一台设备。
- 旧控制台将 M1/A1 也登记到通用 TC1 主题。存在同账号明确 M1/A1 登记时，以明确型号为准，不保留多余的 TC1 占位记录。
- 跨账号归属冲突或两个明确产品型号冲突时终止迁移，人工核对，不能静默抢占设备。
- TC1 迁为 Legacy，保留原始主题和 HA 标识。支持 Legacy 原始 JSON 状态及固件保留的 HA 文本状态/控制。切换 TMCP 会改变主题与 HA 标识，不能静默切换。
- M1/A1 转为当前 TMCP 账号主题记录。早期项目协议不再接收，旧固件必须升级才能重新上线。
- 历史 retained 消息不灌入新 Broker，防止旧状态或控制内容污染新协议。新设备重新发布发现与状态。
- SMTP、公开地址、注册策略和联系信息需要从旧配置按新配置字段逐项核对；隔离走查实例使用独立配置，不发送生产邮件。

## 演练与验收

先在独立 Compose 项目、独立端口与独立 runtime 上恢复。不要挂载生产数据库、Docker socket、密码文件为可写，也不要把生产设备批量指向演练实例。

1. 核对账号数、MAC 集合、归属、明确型号和 TC1 Legacy 设置；比较全部密码哈希、盐与迭代次数。
2. 用迁移账号验证 HTTP 登录及真实 MQTT CONNECT/SUBACK，正确凭据成功，错误凭据失败。
3. 验证同账号 TMCP 发现、状态与带 `request_id` 的 `command/result`；验证跨账号主题和早期主题被拒绝。
4. 验证 Legacy 主题和 HA 标识、管理员权限、普通账号无法进入管理接口。
5. 浏览器验证默认登录页、自建 Broker 入口、首页核心信息、二级设置、第三方 Broker 和手机布局。
6. 独立客户端验证真实设备查询与采样；模拟消息、浏览器检查、真实设备与 HA 实际加载的结论分别记录。
7. 重启演练服务，检查账号、权限、设备列表和登录恢复。

## 正式切换与回退

走查验收后，安排切换窗口：暂停旧平台账号/设备管理写入，重新取得最终备份，校验文件在采集前后没有变化，使用新目录重新迁移并完成上述核对，再切换公开 Web/MQTT 入口。旧服务和目录保留，避免在同一端口启动两个 Broker。新平台的域名、TLS、注册策略与 SMTP 单独验证。

回退时先停止新服务与新写入，再将入口恢复到旧服务；保留新 runtime 供对账。新平台新增账号或修改密码不会自动回写旧 `passwd`，正式切换后发生写入时必须先对账，不能直接覆盖旧库。演练实例删除不会影响生产。GitHub 原仓库删除应安排在历史、构建与迁移验收完成之后。
